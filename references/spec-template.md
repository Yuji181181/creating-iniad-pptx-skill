# スライド仕様書テンプレート

> スライドを生成する前に、この形式で **1 ページずつの仕様書** を書き、ユーザーの承認を得る（plan モード・仕様駆動開発と同じ考え方）。
> 仕様書は `output/<デッキ名>/spec.md` に保存する（出力先は固定）。承認後の生成スクリプトはこの仕様書どおりに作る。

## 書き方のルール
- **全ページを省略せずに書く。**「以下同様」「…」でまとめない。ユーザーがこの仕様書だけで完成形を想像できる粒度にする
- 各ページに **使う見本スライド番号**（カタログの 01〜19）と **レイアウト名** を必ず書く
- 文言は **スライドに載せる文そのもの** を書く（要約や「〜について説明」ではなく、実際の箇条・コード・表のセル）
- 色の指定（赤字の要点・青字の補足）、図の構成（何をどこに描くか）も書く
- 日英併記のときは英語の文言も書く
- **画像・スクリーンショットを使うページは、その出どころを書く**（「画像: user-images/xxx.png」または「スクリーンショット: 何を・どのコマンドで撮るか」）
- 情報量の見積もり（「lvl0 が 4 項目」など）がカタログの目安を超えるページは、分割案を添える

## 形式

```markdown
# <デッキのタイトル> 仕様書

## 全体
- 科目名 / 回: <例: アルゴリズムとデータ構造 / 第N回>
- 言語: 日本語のみ / 日英併記 / 英語のみ
- Copyright の年: <例: 2026>
- ビジュアル: シンプル / 中間 / リッチ
- 情報密度: 余白多め / 標準 / 情報量多め
- 枚数: <N> 枚
- 対象・ねらい: <誰に、何を理解してもらうか（1〜2 行）>

## 構成（一覧）
| # | 見本 | タイトル | 種類 |
|---|---|---|---|
| 1 | 01 講義表紙 | <科目名 / 第N回 タイトル> | 表紙 |
| 2 | 04 標準 | 本日の内容 | 本文 |
| … | … | … | … |

## ページ詳細

### 1. <タイトル>
- 見本 / レイアウト: 01 講義表紙 / INIAD 講義表紙（担当者つき）
- 内容:
  - 科目名: <文言>
  - タイトル: <文言>
  - 担当者欄: <担当者名 / 英語表記 / 連絡先。未定なら「担当者名」のまま と明記>

### 2. <タイトル>
- 見本 / レイアウト: 04 標準 / INIAD タイトル+本文
- 内容:
  - ● <lvl0 の文言>
    - ■ <lvl1 の文言>
  - ● <lvl0 の文言>（<強調する語> を赤字）

### 3. <タイトル>
- 見本 / レイアウト: 09 コード + 実行結果 / INIAD タイトルのみ
- コード:
  ```python
  <実際に載せるコード>
  ```
  - 注目箇所（#C00000）: <例: append, pop>
- 実行結果:
  ```
  <実際に載せる出力>
  ```
- 要点（赤字）: <文言>
- 補足（青字）: <文言>

### 4. <タイトル>
- 見本 / レイアウト: 06 表 / INIAD タイトルのみ
- 表の上の説明: <文言>
- 表（コード列: <列名>）:
  | 見出し1 | 見出し2 | … |
  |---|---|---|
  | … | … | … |
- 表の下の注記（赤字）: <文言>

### 5. <タイトル>
- 見本 / レイアウト: 05 図 + 右説明 / INIAD 図+説明（右本文）
- 図（左半分）: <何をどう描くか。例: 縦に A・B・C を積んだスタック。一番上の C を赤枠。上に push（赤・下向き矢印）と pop（青・上向き矢印）>
  - または 画像: user-images/<ファイル名>（ユーザー提供の画像）
  - または スクリーンショット: <対象>（例: 「pycode で DataFrame を表示するセル 1〜2 を撮る」「https://… の #main 要素」）
- 右の説明:
  - <文言>
  - <強調の文言>（赤字）
```

## 承認の取り方
1. 仕様書を保存したら、ファイルのパスと「構成（一覧）」の表をチャットに示す（ページ詳細はファイルで読んでもらう）
2. `AskUserQuestion` で承認を聞く。選択肢は「承認して生成する」「修正したい（内容を入力）」「構成から見直す」
3. 修正の指示があれば仕様書を直し、**変更点を要約して** もう一度承認を聞く。承認されるまで生成スクリプトを書かない
4. 生成や QA の途中で仕様から外れる変更（ページの分割・統合、文言の短縮など）が必要になったら、仕様書を先に直してから生成し直し、最終報告で変更点を伝える
